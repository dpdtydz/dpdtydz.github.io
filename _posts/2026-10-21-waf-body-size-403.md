관리자 화면 하나에서 저장 버튼이 갑자기 먹통이 됐다. 같은 화면의 조회(목록 불러오기)는 멀쩡한데, 저장(POST)만 **403 Forbidden** 을 받기 시작했다.

인증이 풀렸나 싶었지만 그랬다면 401 이 떠야 한다. 라우팅이 깨졌다면 404 나 405 다. 그런데 403 인데다 **같은 화면에서 GET 은 되고 특정 POST 만** 막힌다. 이 조합이 범위를 꽤 좁혀 준다.

(이 글의 수치는 설명을 위해 단순화한 값이다.)

---

## 403 의 몸통부터 본다

403 을 만나면 상태 코드만 보지 말고 **응답 본문**을 봐야 한다. 여기서 모든 게 갈렸다.

```
HTTP/1.1 403 Forbidden
Content-Length: 581
Content-Type: text/html

<html><head><title>403 Forbidden</title>...</html>
```

애플리케이션(Spring)이 막은 거라면 평소처럼 JSON 에러가 왔을 것이다.

```json
{ "resultCode": "403", "message": "..." }
```

그런데 돌아온 건 짧은 HTML 이었고, 크기가 **581바이트로 늘 일정**했다. 요청이 달라도 응답이 그대로라는 건, 요청을 들여다본 쪽이 애플리케이션이 아니라는 뜻이다. **요청이 앱에 닿기도 전에 앞단에서 잘렸다.** 우리 앞단은 클라우드 게이트웨이의 WAF(Web Application Firewall) 였다.

> **판별 포인트:** 403 인데 응답 본문이 애플리케이션 JSON 이 아니라 게이트웨이의 정적 HTML 이면, 앱이 아니라 앞단(WAF/프록시)을 의심한다. 응답 크기가 요청과 무관하게 일정한 것도 신호다.

---

## GET 은 되고 POST 만 — 그러면 본문이다

WAF 가 막았다면 다음 질문은 "무슨 규칙에 걸렸나"다. 여기서 "GET 은 통과, 특정 POST 만 차단"이 결정적이다.

- 경로·메서드 기반 차단이면 그 화면 자체가 안 떠야 한다. GET 은 멀쩡하다.
- 헤더·쿠키 문제면 같은 세션의 GET 도 같이 막혀야 한다. 역시 멀쩡하다.
- GET 과 POST 의 가장 큰 차이는 **요청 본문(body)** 이다.

그래서 본문 쪽을 의심하게 된다. WAF 정책에는 본문과 관련해 크게 두 가지가 걸려 있다.

| 설정 | 하는 일 |
|---|---|
| 요청 본문 최대 크기 | 이 크기를 넘으면 요청 자체를 거부 |
| 본문 검사 한도 | 이 크기까지만 규칙(SQLi·XSS 등) 검사 |

기본값은 **128KB(131,072바이트)** 다. 사용하는 규칙 세트가 최신 계열이면 2MB 로 더 크다. 문제는, **본문 크기 초과도 403 으로 떨어진다**는 점이다. 로그를 열어 보면 `Request body length exceeded the limit` 같은 메시지가 찍힌다. 즉 **"규칙 위반 403"과 "크기 초과 403"을 응답 본문만으로는 구분할 수 없다.** 둘 다 똑같이 581바이트짜리 HTML 이 온다.

그래서 **방화벽 로그**가 필요하다. 하지만 로그 접근을 기다리는 동안에도, 가설은 직접 재현해 확인할 수 있었다.

---

## 내용 말고 크기만 바꿔 보낸다 — 이진 탐색

막힌 저장 요청의 본문 크기를 재 보니 **약 154KB** 였다. 128KB 한도를 넘는다. 가설이 섰다: 규칙 위반이 아니라 **크기 초과**다.

이걸 가르려면, 규칙에는 걸릴 리 없는 **의미 없는 본문**을 크기만 조절해 던져 보면 된다. 공격 패턴이 전혀 없는 본문이 크기 때문에 막힌다면, 범인은 규칙이 아니라 크기다.

```
본문 ~131,000바이트  → 200 OK   (통과)
본문  131,072바이트  → 403       (차단, 정확히 128KB)
```

경계가 **정확히 128KB** 에 떨어졌다. 애플리케이션 로직과 무관한 더미 본문이 이 크기에서 갈렸으니, 규칙 위반이 아니라 **본문 크기 한도**가 범인으로 확정됐다. (뒤에 받은 방화벽 로그의 `body length exceeded` 메시지가 이걸 재확인해 줬다.)

> 내용이 아니라 **크기만** 바꿔 경계를 찾는 건, 변수 하나만 움직이는 이진 탐색이다. "규칙 vs 크기"처럼 응답이 똑같아 안 갈라지는 두 원인을, 내용을 비워 규칙 쪽 변수를 죽이고 크기 쪽만 살려서 가른다.

---

## 왜 그 저장만 컸나

범인은 찾았는데, 더 근본적인 질문이 남는다. 저장 본문이 왜 154KB 까지 부풀었나.

그 화면은 **"바뀐 것만"이 아니라 목록 전체를 매번 다시 전송**하는 구조였다. 항목이 수백 개인 사용자는 저장 한 번에 전체 목록을 통째로 올려 보냈고, 그게 128KB 를 넘겼다. 항목이 적은 사용자는 멀쩡히 저장됐기 때문에, "특정 저장만" 막히는 것처럼 보였던 것이다.

---

## 해결 두 갈래

원인이 둘(앞단 한도 + 비대한 본문)이라, 해결도 양쪽에서 잡았다.

**① 운영 쪽 — WAF 화이트리스트.** 이 트래픽은 외부 공격이 아니라 내부 관리자 화면의 정상 저장이다. 해당 서버 IP 대역을 WAF 예외로 등록하면 그 경로의 본문 검사·크기 제한을 비껴간다. 이건 인프라 담당(devops) 협조가 필요한 일이라 분리해 요청했다.

**② 애플리케이션 쪽 — 본문 축소.** 화이트리스트가 반영되기 전까지도 막혀 있으면 안 되니, 전송 본문 자체를 줄였다. 저장에 꼭 필요 없는 파생·중복 필드를 응답에서 빼서 **154KB → 72KB** 로 절반 이하가 됐다. 한도 아래로 확실히 내려간다.

단, 필드를 빼면 저장 결과가 달라질 위험이 있다. 그래서 **축소 전후가 같은 결과를 내는지 테스트로 못 박았다.** "본문을 줄였다"가 아니라 "줄여도 같다"를 보장하는 게 핵심이다.

```
축소 전 본문  →  저장 결과 R
축소 후 본문  →  저장 결과 R   (동등성 테스트로 고정)
```

두 갈래를 다 둔 이유는, 한쪽은 즉시(앱) 다른 한쪽은 근본(인프라)이기 때문이다. 앱 축소는 지금 당장 막힘을 푼다. 화이트리스트는 "목록이 더 커지면 또 128KB 를 넘을 수 있다"는 재발 여지를 닫는다.

---

## 배운 것

- **403 은 본문부터 본다.** 애플리케이션 JSON 이 아니라 게이트웨이 HTML 이면, 범인은 앱이 아니라 앞단(WAF·프록시)이다. 응답 크기가 일정한 것도 신호다.
- **"GET 되는데 특정 POST 만 403"이면 본문을 의심한다.** 인증(401)·라우팅(404/405)이 아니라 요청 본문 크기·본문 검사 규칙을 먼저 본다.
- **응답만으로 "규칙 위반 vs 크기 초과"는 안 갈라진다.** 둘 다 같은 403 HTML 이 온다. 확정하려면 방화벽 로그를 확보하거나, 내용을 비운 더미 본문으로 크기 경계를 직접 찾는다.
- **근본 원인은 "매번 전체를 보내는" API 설계였다.** 바뀐 것만 보내는 구조였다면 본문이 애초에 크지 않았다. 앞단 한도는 증상을 드러냈을 뿐이다.
